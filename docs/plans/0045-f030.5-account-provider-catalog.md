# F030.5: Account/provider catalog architecture

> 本文件只做设计，不改实现。`#207` 的 GLM 标签 + 常用模型 chip 是可发现性补丁，
> 先保持 open，不作为本设计的架构基础；是否保留由本设计决定。

## 1. 结论

1. **固定 v1 vendor catalog 作为 MVP 可以接受，但不能作为长期 provider 真相源。**
   它把 vendor、wire protocol、env key、模型建议混在一张手写表里，必然与 pi 的 provider
   catalog 漂移；GLM 标签问题只是症状。
2. **Clowder 值得学的不是“动态 provider 列表”，而是分层：固定 client/protocol，账户用
   `baseUrl + models` 表达 vendor/gateway。** Clowder 也没有在账号表单里动态拉 models.dev；
   它固定的是“怎么发请求”，不是“有哪些厂商”。
3. **目标：provider/model 元数据从 pi catalog 派生；account 增加 protocol/baseUrl/models/
   modelAliases/envVars；保留 capability allowlist，但不再手写 vendor 表。**

## 2. 现状

- `packages/superagentteam-daemon/src/domains/account/providers.ts` 的
  `ACCOUNT_PROVIDERS` 是手写 vendor 列表（10 个），`GET /api/providers` 直接返回它。
- `packages/superagentteam-web/src/components/agent/AccountsModal.tsx` 用固定下拉渲染
  provider；models 是自由文本，`suggestedModels` 是 #207 的局部补丁。
- `AccountConfig` 当前核心字段：`provider`、`models`、`apiUrl`、`apiKeyRef`。
- pi 已有更大的 provider/env/model catalog（`packages/ai` 的 provider 定义、env-api-keys、
  生成的 provider model data）；daemon 的列表只是它的手写子集。

问题：

1. **重复真相源**：provider id / env key / model catalog 在 pi 与 daemon 各一份，会漂移。
2. **vendor 与 protocol 混淆**：许多 OpenAI-compatible 网关被迫各占一个 provider id，
   新增兼容厂商要改 daemon code。
3. **模型不可发现/不可校验**：自由文本拼错要到运行时才失败；`suggestedModels` 只覆盖少数。
4. **扩展成本**：每加一个 provider/模型建议都要改 daemon + 发布；UI 看起来像全集，实际不是。

## 3. Clowder 参考（只读实现，非 runtime 依赖）

| 维度 | Clowder 做法 | 证据 |
|---|---|---|
| 账户模型 | `AccountConfig`：`authType`、`clientId`、`baseUrl`、`models`、`modelAliases`、`envVars`；账户本身是 provider profile | `packages/web/src/components/hub-accounts.types.ts`、`packages/api/src/config/account-store-format.ts` |
| 固定层 | 固定 **client/protocol**：`anthropic`、`openai`、`google`、`kimi`、`opencode`、`acp` | `packages/web/src/components/UnifiedAuthModal.tsx`、`packages/api/src/routes/accounts-schemas.ts` |
| API-key 账户 | 要求 `clientId`；schema 的 `baseUrl` 可选，新建 UI 要求填写；`models` 自由输入；不要求 vendor 白名单 | `packages/api/src/routes/accounts.ts`、`accounts-schemas.ts` |
| 模型来源 | 用户输入；没有在账号表单里动态拉 models.dev | `UnifiedAuthModal.tsx` |
| 安全边界 | 官方域名 → client family 校验，防止 key 跨官方域名泄漏 | `packages/api/src/config/provider-credential-policy.ts`、`packages/shared/src/types/client-routing.ts` |
| provider 字段 | OpenCode 场景的 env-map 模板，不是全局 vendor catalog | `packages/web/src/components/hub-cat-editor.payload.ts` |

**取舍**：Clowder 的 `clientId` 也是固定 enum——固定本身不是问题；它固定的是运行时可执行的
协议，而不是全量厂商。我们应学它的分层，不应照搬它的 profile/quota/Codex 复杂度。

## 4. 目标架构

### 4.1 三层分离

1. **Protocol/client（capability 层，固定 allowlist）**
   - 表示 runtime 怎么发请求：例如 `openai-compatible`、`anthropic`、`google`、`kimi`；
     `opencode`/`acp` 只在 SuperAgentTeam 真有对应 carrier 时加入。
   - 从 pi provider 的 `api`/client 定义派生；新增协议才需要 code。
2. **Provider metadata（目录层，派生）**
   - `provider id`、label、默认 env key、官方域名、默认 baseUrl、已知 models。
   - 从 pi 的 provider 定义、env-map、model data 生成一份 catalog artifact；daemon 只读。
3. **Account config（数据层）**
   - `protocol`、`provider`、`baseUrl`、`models`、`modelAliases`、`envVars`、credential ref。
   - 任意 OpenAI-compatible gateway 可用 `protocol + baseUrl + models` 表达，不必新增 provider enum。

### 4.2 服务端 contract（提案）

`GET /api/providers` 返回派生视图，而不是手写列表：

```json
{
  "providers": [
    {
      "id": "zai",
      "label": "Z.AI / 智谱 GLM",
      "protocol": "openai-compatible",
      "envName": "ZAI_API_KEY",
      "baseUrl": "https://api.z.ai/api/coding/paas/v4",
      "officialDomains": ["z.ai"],
      "models": ["glm-5.2", "glm-5-turbo", "glm-4.7"],
      "supportsBaseUrl": true
    }
  ]
}
```

- `GET /api/models?provider=<id>`（或包含在 provider view 中）返回已知 model id；UI 用于建议，
  不强制；自定义 model 仍允许，运行时做一次可读校验。
- provider view 由 build-time 生成的 `provider-catalog.json` 提供；CI 对比 pi catalog，
  防止手写漂移。不要在每个请求里访问 models.dev。

### 4.3 账户 create/update

```json
{
  "displayName": "GLM coding",
  "protocol": "openai-compatible",
  "provider": "zai",
  "baseUrl": "https://api.z.ai/api/coding/paas/v4",
  "models": ["glm-5.2"],
  "modelAliases": {},
  "envVars": {},
  "credential": { "kind": "env", "envName": "ZAI_API_KEY" }
}
```

- 旧账户只有 `provider`：按 provider catalog 推导 `protocol` 和默认 `baseUrl`，保持 id/ref 不变。
- 自定义 gateway：`provider` 可空或 `"custom"`，必须有 `protocol + baseUrl + models`；
  不把 custom 写进全局 provider catalog。

## 5. 迁移与阶段

- **F030.5a Catalog 派生（不改 account schema）**：从 pi provider/env/model 数据生成
  provider view；`/api/providers` 改为派生；`suggestedModels` 从同一 catalog 来；加 parity test。
- **F030.5b Account schema 扩展**：加 `protocol`、`modelAliases`、`envVars`；旧 `provider`
  推导 protocol；additive migration，读旧写新。
- **F030.5c UI**：provider 下拉按 protocol 分组；选择 provider 后 model 建议；custom gateway
  模式；GLM 无需 label patch。
- **F030.5d 收口**：删除手写 vendor 表（或保留为 capability filter）；CI 加“禁止手写 provider
  列表”的 guard；runbook/feature docs 更新。

## 6. 安全边界

- 官方域名 → provider family 校验（参考 Clowder `provider-credential-policy.ts`），防止 key
  被发送到另一家官方 endpoint。
- 自定义 baseUrl 只允许 http/https，拒绝 userinfo；凭据仍只写不回显。
- env key 仍走允许的 `[A-Z_][A-Z0-9_]*` 形式；不得把 provider 默认 env 暴露成 secret。
- Catalog 是 build-time 生成的可审计 artifact，不在请求期访问外部 catalog。

## 7. 非目标

- 不在本设计里做 OAuth / Claude / Codex 登录（F030 v1 明确排除）。
- 不改变 pi runtime 支持的 provider 能力；只让 account 层正确表达它。
- 不做请求期动态 models.dev 发现；用 pinned/generated catalog。
- 不照搬 Clowder 的 Codex quota/native login/multi-OAuth profile 复杂度。
- 不把 #207 的 chips 当作最终模型目录方案；它最多作为过渡态。

## 8. 待 operator / review 决定

1. **v1 暴露范围**：全量 pi API-key provider，还是“curated support tier + capability filter”？
   我建议后者：UI 明确标 supported，catalog 仍从 pi 派生，不手写 vendor 表。
2. **protocol enum**：SuperAgentTeam 实际需要哪些 protocol？先支持 openai-compatible /
   anthropic / google / kimi，还是也保留 opencode/acp？
3. **model 校验**：只建议 + 运行时警告，还是对官方 provider 严格拒绝未知 model？
   我建议“建议 + 允许 custom”，官方 provider 可给强 warning。
4. **catalog 生成位置**：build-time artifact（推荐）还是 daemon 运行时 import pi 包？
5. **旧账户迁移**：是否需要一次性写回 `protocol`，还是永久允许按 `provider` 推导？
6. **#207 去留**：保持 open 等设计决定，还是先合并作为过渡 UX？

## 9. 验收（设计层）

- [ ] `ACCOUNT_PROVIDERS` 不再作为手写 vendor 真相源；provider/env/model 有单一生成源。
- [ ] 新增一个 OpenAI-compatible provider/model 不需要 daemon code change（或只需 catalog data）。
- [ ] GLM 等 provider 的 label/models 来自 catalog，不靠一次性 label patch。
- [ ] 旧 accounts 全部可读、可运行，ref/id 不变。
- [ ] `GET /api/providers` 返回 protocol/provider/env/baseUrl/models 元数据；model 建议可用。
- [ ] custom gateway（protocol + baseUrl + models）有明确 UI 路径和测试。
- [ ] official-domain key 边界、secret 不回显、CSRF/session 边界有测试。
- [ ] CI 有 catalog parity/drift guard，防止再次出现手写列表与 pi 漂移。
